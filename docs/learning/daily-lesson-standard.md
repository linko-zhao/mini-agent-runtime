# 每日学习文档：图解设计与测试先行

> 学习目标：只看本页的说明、骨架和测试，你就能实现当天模块。
> 参考代码用于最后核对；无需先读答案才能开始。

这是后续课程的交付标准。[Day 08](agent-runtime-day-08.html) 是首篇样板；Day 09–15 已按同一规范更新，Day 14 采用装配与集成复盘。Day 01–07 尚未改写。

## 1. 先降低阅读负担

- 每天先写一句话：“今天实现____，让____能够____。”
- 核心讲解每段一件事，通常不超过三句；长背景与扩展资料折叠。
- 每节先给结论，再给一个具体例子。一个例子贯穿全页，不频繁切换业务。
- 首次出现术语时立即解释。例如：“注册表：按工具名查找工具的容器。”
- 同一个概念保持同一个名字。不要让“工具目录”“注册中心”“Registry”无说明地交替出现。
- 正文字号建议 18px、行高 1.8、正文宽度约 38–42em。手机单列；代码独立横向滚动，正文不横向溢出。
- 正文不依赖颜色、悬停或外部资源。折叠区能用键盘打开，图有等价文字。

## 2. 每天固定的阅读路线

### A. 今天只解决什么

写明一个具体需求、目前遇到的问题和本日完成结果。

列出本日范围与暂不处理的问题。不要把整周能力全塞进一天。

### B. 先看一次具体运行

示例结构：

```text
输入是什么？
    ↓ ① 谁先收到它？
中间产物是什么？
    ↓ ② 谁读取它，作出什么判断？
结果交给谁？
    ↓ ③ 失败时停在哪里？
最终可观察结果是什么？
```

正式 HTML 至少有两幅内嵌图：职责关系图、编号运行图。

图中每个箭头写明数据。若有装配与运行两个阶段，分成两幅小图；图后用短句走同一个输入。

失败路径单独用一个反例说明，不在主图上堆满所有分支。

### C. 每个概念讲三件事

1. **是什么**：不用接口名也能说懂的一句话。
2. **为什么需要**：没有它时，当天场景会出现什么具体问题？
3. **怎么落到代码**：由哪个字段、接口或方法承担职责？

例如：“工具说明让模型知道能选什么；工具对象负责真正执行。两者分开，列出说明时就不会访问业务数据。”

### D. 为什么这样设计

每个公开类型/方法单独一张短卡片：

```text
名字：
职责：
字段/参数：含义、单位、来源、是否允许为空、谁拥有/能否修改。
返回：具体值、是否有部分结果、调用方下一步做什么。
失败：可识别的错误、是否保留原因链、会不会发生副作用。
状态：读取/写入哪些状态；取消和并发有什么承诺。
设计理由：它解决哪个问题；直接写在调用方会有什么代价。
```

不是所有东西都要抽象成接口。只有确有替换、隔离或测试需求时才引入接口，并说明代价。

### E. 行为契约：不用读答案也知道怎么写

每条规则给编号，并与一个或多个测试对应。

| 规则 | 触发输入/前置状态 | 可观察结果 | 对应测试 |
| --- | --- | --- | --- |
| R1 | 一个确定的合法输入 | 确定的返回值或状态变化 | 完整测试中的准确名称 |
| R2 | 一个确定的非法输入 | 错误及禁止发生的副作用 | 完整测试中的准确名称 |
| R3 | 依赖返回指定错误 | 原因链与调用次数 | 完整测试中的准确名称 |

空值、重复、未知对象、顺序、拷贝与取消语义都必须说明，不让测试偷偷添加文档没讲过的规则。

“支持取消”必须说明在哪个边界检查、哪个下游接收 ctx、取消后还可能完成什么操作。

### F. 可以直接编译的骨架

页面内给出完整文件：package、import、结构体、接口、构造函数、全部待实现方法。

每段代码前标明目标路径与“新增 / 修改 / 复用”。只复用已在前序建立的类型；必要前置文件列全。

方法签名必须与测试完全一致。方法体使用明确 TODO，例如 `panic("TODO: implement Register")`；不能填入核心算法。

已有方法只列需要修改的片段及定位方法，不要求覆盖学习者整份文件。迁移必须解释旧签名、对应新签名和所有调用点。

根 `internal` / `cmd` 是练习目标；`examples` 是累计参考答案。两套包类型不要混用。自动化只提供应用说明，不能替学习者填好练习实现。

### G. 完整的测试文件

交付真实 `_test.go`，包含全部 import、fixture、fake 和断言。HTML 内全文可复制，不能依靠远端下载才能练习。

先验证核心规则，再验证失败与边界。使用记录调用次数/参数的 fake，检查设计的不变量；不要依赖真实 API Key、网络或已有参考答案。

只测试公开行为，不要求某种 map、锁或私有辅助函数。若承诺并发安全，要提供有意义的并发测试并执行 race；无并发承诺则说明范围。

外部失败用 `errors.Is/As` 检查必要语义，不绑定未知错误的完整文本。取消/超时优先用可控 fake 和同步信号，不依赖固定 sleep 猜测执行顺序。

新增装配任务同样要给待实现函数签名、可调用的夹具及完整集成测试。不能把周末任务写成“阅读既有集成测试”。

### H. 一次只完成一步的实现任务

每步使用同一格式：

```text
目标：实现哪条规则，为什么现在做。
位置：文件与方法名；新增还是修改。
输入 → 输出：用本页同一场景给具体值。
动作：本步只补哪些行为，哪些已由依赖负责。
验证：从仓库根执行的准确命令；应匹配到的测试。
完成证据：测试断言或可观察结果；下一步入口。
卡住时：一个逐级提示，默认折叠，不直接展示答案。
```

保留 20 分钟官方阅读、80 分钟编码、20 分钟测试复盘。阅读先给待回答的问题和产出；Eino 只作对照，不要求照搬它的接口。

80 分钟分成 3–5 个小步。每步对应一组确定的测试，避免一句“完成模块”覆盖所有实现。

### I. 红 → 绿 → 重构

1. **确认环境**：说明 Go 版本、工作目录、所需前置章节与文件。
2. **编译**：如 `go test ./internal/目标包 -run '^$'`。这只验证可编译，不算行为通过。
3. **红灯**：运行精确目标测试；确认确实匹配测试，失败来自 TODO 或未满足的业务断言。
4. **绿灯**：由学习者补实现；按小步先运行目标测试，再运行整个目标包。
5. **重构**：在全部行为通过后整理重复逻辑，再运行同一组测试和受影响累计回归。

正式页面必须把“目标包/目标测试”替换为真实名称；不把上述命令模板当可运行交付。

参考验证放在独立路径或临时工作树，不通过修改测试 import 让测试绕到答案。若验证时需要临时转换包路径，记录对应规则，业务断言必须保持一致。

### J. 完成标准与参考答案

分别列出：

- **实现验收**：哪些命令和断言通过，副作用/错误/取消行为是否符合契约。
- **理解验收**：不看代码讲一次数据流；提出一个需求变化并指出改哪层、为什么。

完整参考代码最后默认折叠或独立存放。提示与答案分层，学习者可以自行选择是否查看。

最后用两句解释今天解决了什么、明天为什么需要新增能力。

## 3. 发布前检查：由生成者完成

- [ ] 只看问题、图、契约、骨架和测试，就能实现模块。
- [ ] 概念先解释再出现；每个字段和方法都有具体职责。
- [ ] 每条行为规则都有测试；测试没有新增隐藏规则。
- [ ] 骨架和完整测试一起能编译；依赖与文件路径明确。
- [ ] 运行目标测试确实有用例执行，并因未实现行为失败。
- [ ] 同一套行为测试对兼容参考实现通过；没有跳过或空断言。
- [ ] 受影响累计回归通过；尚未执行项明确标为“未执行”。
- [ ] 页面明确区分参考实现验证结果与学习者练习状态。
- [ ] 检查移动端、代码横向滚动、键盘操作、离线图示与清单保存。
- [ ] 保留课程日序、旧接口衔接、首页周模块和原有学习者代码。

这份规范本身不代表某一日练习或其测试已经验证通过。
