Day 11 / 56 · 工具可见性、执行授权与审计

模型提出调用意图，宿主决定是否有权执行。把工具描述、调用策略和权限判断放回各自职责。

阅读 20 分钟编码 80 分钟测试复盘 20 分钟

为什么隐藏工具还不够？

能解释可见性和授权的区别，沿现有 Agent 数据流添加执行前的权限检查，并用零执行反例验证拒绝没有越过副作用边界。

Day 08 的注册表知道有哪些能力，WithVisibleTools 决定模型看到哪些描述。Day 09 保证同批调用 ID 和结果对应，Day 10 约束耗时、重试资格与结果预算。现在用户只是知识库读者，模型却请求 publish_document。即使没有向模型展示该工具，Runtime 若只按已注册名称分派，仍可能执行写入。

今天解决“这个可信调用者能否执行这项能力”，而不是继续调整检索工具的业务算法。权限由应用及后端决定；提示词里写“不要调用”或模型自报身份不能代替授权。整个课程仍按既定进度推进，不依据学习者的根 internal/cmd 实现判断完成。

先走通允许与拒绝两条过程

装配：Store → Meta/Invoke → Registry.Tools → Day10 WithPolicy
    → Agent.New(..., WithVisibleTools(...), WithAuthorizer(policy))
请求：宿主认证会话 → WithPrincipal(ctx, Principal{ID:"knowledge-reader"})
    → Model.Generate → assistant.ToolCalls → 保存原 assistant
    → 整批 ID/已注册名称检查 → 整批 Authorize(ctx, Call)
       ├ 任何拒绝/故障/取消：决策事件 → RunFailed
       │                    本批 Execute 次数为0，不再调用模型
       └ 全部允许：决策事件 → ToolStarted
              → Policy.Execute → Invoke → Store（仍检查资源级权限）
              → ToolCompleted → tool{原 ToolCallID, Content}
              → Model.Generate(完整历史) → 最终答案

先预测：同批 [允许的读取 A，拒绝的写入 B]。我们的实现先完成整批授权，因此 A 也不执行。审计中可能已经有“A 允许”决策，但它不是“A 已执行”。这不是事务：整批允许后，后端失败或取消仍可能造成部分操作已发生。

离线脚本模型可证明 Runtime 对恶意或错误调用仍执行检查；不能证明真实认证、租户 ACL、后端权限、实时撤权或审计存储已经部署。

三道边界分别负责什么？

边界输入/目的不能替代
可见性 WithVisibleTools选择给模型的描述，降低误选和上下文成本不删除执行注册，不是访问控制
执行策略 WithPolicy限制时间、重试资格和输出预算ReadOnly 配置不授予读取权限
执行授权 WithAuthorizer使用可信主体和服务端能力表，允许或拒绝调用本课工具级规则不替代文档/租户级后端 ACL

课程采用静态、不可变的工具级能力快照：read 与 write 是独立授权；未声明工具、未知或缺失主体默认拒绝。不同用户的 Principal 放在各自 Run 的 context，不存进共享 Agent 字段。实际服务中只能由完成认证的宿主注入；本课的 reader 字符串是离线演示身份。

为了保持前序 API 兼容，省略 WithAuthorizer 仍是旧行为，不会自动启用权限检查。宿主对不可信模型开放工具时必须显式配置授权；WithAuthorizer(nil) 则在 New 阶段报错。

授权复用 tool.Call（既有 model.ToolCall 的别名），不新建另一套消息类型。Agent 交给自定义 Authorizer 的 Arguments 是副本，避免授权器修改实际执行输入。基线使用命名字段构造 Event；新增 PrincipalID 不要求修改这些构造。历史按位置构造 Event 的外部示例应迁移为命名字段，事件 switch 需要识别新类型。

设计选择与代价

选择为什么与限制
整批开始前授权后项被拒绝时不会先执行前项；代价是一次拒绝阻止本批其他合法调用。只校验能力，不保证业务参数和资源 ACL 都已通过。
拒绝或授权服务错误终止 Run避免把授权失败当作普通工具结果让模型反复试探。errors.Is 能识别 ErrForbidden；原因链返回可信宿主，不进入模型历史。
配置快照不变、主体来自 context可在并发请求间共享，降低串用户风险；不提供实时撤权。长任务和后端仍需当前资源级鉴权。
审计复用 EventSink不引入第二套观测系统；只有同步信号，没有落盘、可靠交付或抗篡改保证。后续可观测性章节再演进。

权限检查发生在 Day10 Policy 重试外部；当前一个逻辑调用只按快照授权一次，不在每次内部尝试重新授权。写入本来就不自动重试。未来如果要求实时撤权或审批，应定义新的执行协议，而非修改模型提示词。

80 MIN · BUILD

四项连续练习：先预测行为，再对照参考实现

任务一 · 20 分钟：划清三个集合，建立可信主体

为什么做：注册、模型可见和有权执行不是同一个集合。操作与观察：5分钟画出三个集合，10分钟阅读 access.go 的输入复制与默认拒绝，5分钟用 reader/writer 两类主体手算授权结果。下列是既有参考实现的接口摘录，不是独立程序：

type Principal struct { ID string }
type Authorizer interface {
    Authorize(context.Context, Call) error
}
// 只允许可信宿主在认证后调用：
// ctx = tool.WithPrincipal(ctx, tool.Principal{ID: session.SubjectID})

完成证据：能解释为何不能从模型 Arguments 取 SubjectID；新增工具若没有能力规则会被拒绝；write 不隐式包含 read。修改构造输入后，已经建立的能力快照不改变。

任务二 · 20 分钟：将授权放进已有批次边界

为什么做：仅在业务工具里散落检查难以统一失败语义，也可能在后项拒绝前已执行前项。操作与观察：10分钟跟踪 agent.go 中名称/ID 检查后的授权循环，再看真正 Execute 所在的第二个循环；5分钟构造 [read,write] 反例；5分钟解释 Authorizer 错误或 context 取消为何终止。

完成证据：TestAuthorizationDeniesWholeBatchBeforeExecution 的读取和写入计数都为0，模型只调用一次，RunFailed 恰好一次且没有 ToolStarted。自定义授权器不能通过修改 Arguments 改变实际工具输入。

任务三 · 25 分钟：装配真实路径，验证可见性不是授权

为什么做：新增接口必须接回实际 Agent，而不是停留在设计稿。操作与观察：10分钟对照 cmd/knowledge 中的能力表、主体注入和原 Day10 包装；10分钟运行 cmd/access 的隐藏写工具反例；5分钟比较“隐藏但权限允许的读取”和“可见但权限拒绝的写入”。现有公开 New/Run、Meta/Invoke 和消息类型均不更换。

// 摘录，完整装配见 examples/cmd/knowledge/main.go
authorizer, err := tool.NewCapabilityAuthorizer(
    map[string]tool.Capability{
        "search_knowledge": tool.ReadCapability,
        "get_document": tool.ReadCapability,
    },
    map[string][]tool.Capability{
        "knowledge-reader": {tool.ReadCapability},
    },
)
// 检查 err 后，在原 New 调用增加 agent.WithAuthorizer(authorizer)。

完成证据：knowledge 仍完成检索 → 读取 → 回答；access 输出授权拒绝且写入次数为0。更换工具可见集合不会自动改变授权结果。

任务四 · 15 分钟：读懂决策审计，解释尚未解决的问题

为什么做：权限判断必须能追踪，但“记录允许”不能混同“操作成功”。操作与观察：5分钟核对新增 EventToolAuthorized/EventToolDenied；5分钟沿原 ID 看主体、工具名、Step 和 Status；5分钟推演审计 Sink 阻塞、进程崩溃、授权后权限被撤销会怎样。

完成证据：事件没有参数、正文、令牌或原始错误；允许/明确拒绝/故障/取消分别为 ok/denied/error/cancelled。只有配置 WithEventSink 才有消费者接收记录，授权测试注入了收集器；共享 Sink 沿用同一 SynchronizedSink 包装。能说明这些同步信号不构成持久审计、权限锁、事务或副作用回滚。
