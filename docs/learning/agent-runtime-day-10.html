Day 10 / 56 · 工具执行策略与 Eino 中间件

工具调用成功接回模型后，怎样控制调用的耗时、失败恢复与输出成本？在既有接口外增加兼容策略层。

阅读 20 分钟编码 80 分钟测试复盘 20 分钟

为什么今天要学执行策略？

能解释策略与业务工具、Agent Loop 的职责差异，并能为读取能力选择有限重试、整次超时与结果预算，避免让 Agent 因慢请求、重复副作用或过量正文失控。

Day 08 建立 Meta/Invoke 与注册适配，Day 09 确立批次 ID 检查、顺序执行及消息回填。现在用户希望“检索文档后生成答案”，后端偶发暂时失败；如果把重试写进每个工具，取消、耗时与错误语义就会不一致。如果对所有工具一律重试，创建工单可能发生两次。

今天采用装配时包装一次工具，执行时应用统一策略：不改变 Tool.Execute，不引入第二套 Call/Message。先预测行为，再阅读 Eino 对应入口，最后对照参考实现。

先走通完整 Agent 数据流

装配：Store → SearchKnowledge/GetDocument（Meta/Invoke）
    → Registry.Register → Registry.Tools（旧 Tool 适配快照）
    → WithPolicy（保留 Name/Definition）→ Agent.New → 绑定模型描述
运行：Model.Generate → assistant.ToolCalls
    → Loop 保存 assistant，整批检查 ID/名称
    → EventToolStarted → 策略.Execute（总超时、重试资格）
        → Tool.Execute → Invoke → Store
        ← 暂时失败：仅显式只读且分类允许，有限重试
        ← 成功：检查结果字节预算
    → EventToolCompleted
    → tool{原始 ToolCallID, Content} → Model.Generate → 最终回答

知识检索得到文档 ID 后，读取仍在后续模型轮次。一次内部重试沿用同一逻辑调用，不追加额外 tool 消息；模型下一轮重新发起调用则是新的 Agent 决策。现有事件记录逻辑调用总耗时，并未增加每次尝试的审计事件。

离线 FakeStore 和脚本模型只能验证协议、取消和策略，不证明真实模型会选对工具、后端支持幂等或真实网络重试有效。

为什么这样设计？

决策收益与代价
超时包住全部尝试和等待避免每次重试重置预算造成总耗时失控；更早的父 context/Agent 超时仍优先。取消需要工具合作。
默认一次；显式只读+分类器才能重试避免把模型自报或普通错误当成安全证据。受控 tool.Error、取消/超时不重试；后端暂时性必须由可信分类器识别。
结果超预算返回受控错误保护下一轮上下文；不直接截断 JSON 造成无效结构。当前按字节计数，不能替代 token 预算或阻止上游已分配的大结果。
包装器保留描述和旧接口原 Loop、注册和消息协议不用迁移；尚非 Eino 完整的可组合中间件链，也未实现流式工具。

幂等边界：ReadOnly 由应用配置，不是授权或外部副作用撤销。写入工具今天不自动重试；如服务端明确支持幂等键，后续需定义键的业务范围、存储、过期和确认协议，不能用 ToolCallID 或进程内 map 宣称跨 Run exactly-once。超时之后外部操作可能已经发生。

四项连续演进练习

任务一 · 20 分钟：先预测，再读 Policy 包装

为什么做：把跨业务策略集中起来，保持既有 Tool 调用契约。操作与观察：5 分钟画装配和执行链，10 分钟阅读新增 policy.go，5 分钟对照 Name/Definition 转发。下面是参考实现的接口摘录，不是独立可运行程序：

type Policy struct {
    Timeout time.Duration
    MaxAttempts int
    ReadOnly bool
    Retryable func(error) bool
    RetryDelay time.Duration
    MaxResultBytes int
}
func WithPolicy(t DescribedTool, p Policy) (DescribedTool, error)

完成证据：能说明为什么不修改 Meta/Invoke、Registry.Tools 和 Agent.New；零 Timeout/MaxResultBytes 表示禁用对应限制，零 MaxAttempts 规范化为一次，负配置被拒绝。

任务二 · 25 分钟：理解超时与重试的控制流

为什么做：重试不应绕过取消或扩大副作用。操作与观察：10 分钟跟踪总超时 → Execute → ctx.Err → 错误分类 → 次数限制 → 可取消等待；10 分钟预测第一次失败第二次成功、受控参数错误、等待时取消；5 分钟修改 policy_test.go 的分类器并观察次数断言。每次尝试复制 Arguments，避免业务实现污染下一次输入。

完成证据：只读暂时失败可恢复；取消、超时、受控错误不重试；写工具配置多个尝试在装配时失败；等待使用 timer/select，取消后不会开始下一次尝试。当前延迟固定且默认零，生产退避/jitter 需另行设计。

任务三 · 20 分钟：观察预算怎样影响下一轮模型

为什么做：大结果会消耗上下文，失败策略要在调用层保持一致。操作与观察：10 分钟观察 MaxResultBytes 对中文 UTF-8 字节的计数，10 分钟追踪超限 ExecutionError 如何经既有 Agent 转成受控 tool 消息。对比取消错误如何终止整个 Run。

完成证据：超限原文不进入模型；逻辑调用保持原 ID；tool 事件耗时包含重试；能解释工具失败反馈与 Run 终止的区别。

任务四 · 15 分钟：装配知识工具并演示

为什么做：策略必须落到 Agent 实际路径。操作与观察：先看 cmd/knowledge 如何将 Registry.Tools() 的 DescribedTool 用 WithPolicy 包装，再传给原 Agent.New；示例给读取工具设置1秒总超时和4096字节预算，默认一次尝试，不启用真实网络重试。运行入口验证检索 → 文档读取 → 回答的既有流程。
