# Agent Runtime 学习进度评审框架

## 使用方式

本文件定义可复用的评审方法。每次评审结果单独保存在 `docs/learning/reviews/`，命名为 `YYYY-MM-DD-简短主题.md`；同日多次评审使用不同主题或序号，不覆盖历史结果。每次复盘记录日期、被评审的 commit、工作区状态、计划版本和验证环境；先阅读对应学习日的目标与 Definition of Done，再检查源码、测试和实际命令输出。学习页面存在不代表代码完成，静态代码存在也不等于验收通过。引用具体路径及测试，区分实际结果、静态推断和未验证事项；不要以百分比代替门禁结论。

状态统一为：**已验证**（实现及对应验收实际通过）、**部分实现**（有代码但缺少边界、测试或验收未通过）、**未实现**（没有对应能力）、**未验证**（证据不足或环境阻塞）。逐项填写：计划日/周、目标与验收条件、状态、实现和测试证据、差距与影响、下一步及验证命令。状态针对功能而非学习者本人；计划的阅读和浏览器 localStorage 勾选无法从仓库证明。

评审前必须从目标仓库获取 `main` 的最新提交，例如执行 `git fetch origin main`，核对远端及获取后的完整提交 SHA，并以该提交的代码和学习计划作为评审基线。可使用独立工作树或快照，避免影响当前工作区；在报告中记录获取时间、远端、分支、SHA 和评审工作区状态。若获取或核对失败，应说明阻塞原因，不得把本地旧分支冒充最新 `main` 开始正式评审。

评审顺序：

1. 获取并核对最新 `main` 基线，然后确认计划范围和前置门禁，检查用户输入 → Model → Tool → 消息回填 → Model → 终态的数据流。
2. 分别检查正常流程、错误链、取消和超时、边界输入、并发、隐私及可观测性；记录测试是否真正覆盖对应路径。
3. 运行 `go version`、`go test ./...`、`go test -race ./...`、`go run ./cmd/demo`、`git diff --check`；记录失败原因及环境限制。真实 Provider 验证单独记录，不以 mock 证明线上兼容。
4. 将问题按 P0（崩溃、错误成功或协议破坏）、P1（第一周门禁或核心行为缺失）、P2（后续增强）排序，写出可验证的修复条件；每周第 7 天重新执行集成回归。进入下一周前先解决阻塞门禁。

## 评审报告模板

每次新建独立报告，保留以下信息；不适用或无法验证时说明原因。

```markdown
# 学习进度评审：主题

- 日期与时区：
- 获取时间、远端、分支、完整提交 SHA 及评审工作区状态：
- 计划范围与依据：
- 评审结论及下一阶段门禁：

## 功能与计划对照
| 计划日/周及验收条件 | 状态 | 实现和测试证据 | 差距与影响 | 下一步 |
| --- | --- | --- | --- | --- |

## 问题与改进建议
| 优先级 | 问题、影响与证据 | 验收条件 |
| --- | --- | --- |

## 后续路线
记录尚未实现的计划内容、前置依赖和建议。

## 验证记录
记录环境、命令、实际结果、失败原因及未验证范围。
```
