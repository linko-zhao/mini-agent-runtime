协议能调用了，为什么还要一层适配？

能在不改Agent Loop和消息类型的前提下，将远端工具描述转成本地Spec，将CallTool转成Invoke，解释名称、错误、内容与权限分别在哪里转换。

Day12的MCP Client已完成初始化、能力协商、发现和调用。若现在直接在Agent.Run里写tools/call分支，Loop就需要知道JSON-RPC、分页、远端名称和内容块；下一个后端又会增加分支。前序Meta/Invoke已经是业务能力的共同入口，今天让远端工具实现它。

场景仍是读取知识文档。业务逻辑继续复用GetDocument和FakeStore，不再写一套文档工具。新增的是协议到Runtime的边界。课堂按设计路线推进，不以根internal/cmd中的学习者代码状态作为课题或发布门禁。

先走通完整过程：两个名字、两个ID域

装配：
Host → Client.Initialize → Discover("knowledge", maxPages=4)
     → 远端Descriptor快照 → 本地Meta/Invoke对象
     → 新Registry → Registry.Tools → Day10 WithPolicy
     → Agent.New(WithVisibleTools, Day11 WithAuthorizer)

运行：
Model.ToolCall{ID:"model-call-42", Name:"knowledge__get_document"}
 → Loop保存assistant，检查整批ID/名称 → 本地主体授权
 → Execute → 旧适配器 → remote.Invoke(ctx,args)
 → Client.CallTool("get_document", args)
 → JSON-RPC{id:3, method:"tools/call"} → Server → GetDocument.Invoke
 ← MCP ToolResult → 本地ResultEnvelope JSON
 ← tool{ToolCallID:"model-call-42", Content:结果}
 → Model.Generate(完整历史) → 最终回答

名字不同：模型/注册表/授权表使用本地别名knowledge__get_document；远端协议仍使用原名get_document。ID不同：模型ID由Agent保留，RPC整数ID由Client分配；适配器不把模型ID或Principal塞进arguments。

先预测：模型能看到别名，但reader没有该能力权限。初始化和发现可能已发生，执行授权仍会在Invoke之前拒绝；测试要求后续tools/call次数为0，不是声称整个流程没有协议消息。

脚本模型验证装配、调用关联和结果历史，不证明真实LLM会选对工具。内存Server验证真实JSON报文，但不证明生产网络认证或后端ACL已经部署。

为什么这样设计？

设计直接做法的局限选择与代价
本地别名，远端原名两个Server都叫get_document会冲突，授权表也无法区分来源宿主分配prefix__name；前缀不含下划线，组合最长64字节。部分MCP名称不能直接映射，明确拒绝而非偷偷清洗
完整发现后装配新Registry边翻页边写活动注册表，后页失败会暴露半套目录页数上限、游标循环和重名检查；失败返回nil。注册仍用新Registry，成功后再发布，不热改共享Agent
Meta只读快照每次枚举都访问Server会使绑定依赖网络和目录变化复制Schema，Meta不发远端请求；目录更新需宿主显式重新发现和装配
结果投影显式定义直接连接字符串可能丢图片/结构化内容，还无法判断失败成功返回JSON Envelope；暂只支持文本块，非文本明确失败；真正多模态需扩展消息契约

本地别名不能认证Server，也不能证明远端工具是只读。服务器身份、目录来源和能力分类必须由宿主信任配置；远端annotations/readOnlyHint既不自动授予权限，也不自动配置安全重试。

结果与错误怎样进入下一轮模型？

成功结果统一为以下JSON字符串。多个文本块按顺序放入text数组；structuredContent存在时保留对象，不把它偷偷拼进一段散文：

// 数据示意，不是独立Go程序
MCP结果：
{"content":[{"type":"text","text":"文档正文"}],
 "structuredContent":{"id":"doc-1"}}

本地Invoke返回字符串的JSON内容：
{"text":["文档正文"],"structuredContent":{"id":"doc-1"}}

原GetDocument返回的正文可能本身就是Document JSON，因此演示的text[0]是那段JSON字符串。接口仍返回string，但投影契约清楚可见；不改旧本地工具的输出。

远端情况适配结果Agent行为
ctx取消/超时保留errors.Is语义，不转成普通业务错误终止Run，不继续下一轮
有效MCP结果isError=true受控ExecutionError：remote tool execution failed回填安全摘要和原CallID，模型可据此结束或调整
RPC/传输/失效会话错误受控request failed，Cause供可信宿主诊断；不回填原始Message/Data不自动重连重放；failed客户端仍拒绝后续发送，Loop保留原有限步数
图片/资源等非文本块明确返回ErrUnsupportedContent，不返回前面部分文本不会把部分结果冒充完整成功
畸形文本或structuredContent受控ErrInvalidResult不将畸形数据标为成功结果

Day10的WithPolicy作用在Invoke外侧，对最终投影JSON施加结果预算。受控tool.Error不会触发自动重试；这项保守选择避免把不确定远端执行重放。权限由Day11独立检查，远端错误和正文都不是新的授权指令。

任务二 · 20分钟：把CallTool接成Invoke，选择投影

为什么做：Loop不应理解JSON-RPC，也不能直接信任所有远端结果格式。操作与观察：10分钟跟踪Invoke里的context检查、原名路由、错误分类和ResultEnvelope编码；5分钟预测文本+structuredContent和文本+image两种输入；5分钟看失败时是否有部分正文泄漏。

完成证据：成功保留文本顺序和结构化对象；不支持的块明确失败；RPC私有错误信息不进入模型错误文本；context仍能终止Run。只有新远端别名使用Envelope，旧knowledge工具不变。

任务三 · 25分钟：复用装配链，观察模型第二轮

为什么做：接入新能力应扩展工具边界，而不是在Agent.Run里增加MCP分支。操作与观察：10分钟阅读examples/cmd/mcpagent/main.go，沿已初始化Client→Discover→新Registry→Registry.Tools→WithPolicy→WithAuthorizer走一遍；10分钟运行入口并检查真实回填文档；5分钟对照integration_test.go里的两个ID域。

完成证据：本地别名绑定给模型，远端收到get_document；第二轮历史有原assistant消息和原ToolCallID的tool结果。演示用脚本模型，最终文本不能单独证明成功，必须同时核对工具结果和调用关联。

任务四 · 15分钟：验证拒绝路径与注册冲突

为什么做：适配新协议不能绕开已有权限和错误策略。操作与观察：5分钟把reader的授权清空，观察远端调用计数；5分钟登记两个同别名工具和两个不同Server前缀；5分钟讨论真实Server身份与本地主体的区别。

完成证据：描述可见也可能被拒绝，拒绝后tools/call为0、模型只调用一次；Registry拒绝重名且不替换旧工具。内存夹具在同进程传context，不意味着Principal会自动跨网络；真实服务的认证与资源授权仍是独立边界。
