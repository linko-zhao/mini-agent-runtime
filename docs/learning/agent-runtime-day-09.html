Eino 官方源码阅读

15 分钟 · Eino ToolsNode 执行链

阅读 compose/tool_node.go：定位 ToolsNodeConfig、ToolInput、genToolCallTasks、Invoke、ExecuteSequentially 和 UnknownToolsHandler。比较它如何生成任务、选择顺序/并行执行，再按原调用顺序构建 ToolMessage。

5 分钟 · 中间件边界

继续阅读同文件 InvokableToolEndpoint、InvokableToolMiddleware 和 ToolCallMiddlewares。记录“围绕一次工具调用的策略”如何与业务 Invoke 分开；不要假定框架默认错误行为适合所有 Agent。

阅读产出：标出 Eino 对应符号、画出数据流，并写下一个设计取舍。源码 main 会变化；实际练习时记录所读 commit 或依赖版本。

80 MIN · BUILD

Go 练习与设计任务

20 分钟 · 建立执行器数据流

在独立练习 labs/week02/day09/ 建立 executor.go（可复用 Day 08 的设计稿或自带 FakeRegistry，不依赖前一天实际编码完成）。设计 ExecuteBatch(ctx,calls) 接口与 Result{CallID,Name,Content,Status}。在执行副作用前完成整批检查：名称、调用 ID、重复 ID、工具是否存在、本轮是否允许。ID 缺失不能猜造。

25 分钟 · 顺序执行与错误分类

在 policy.go 写出明确策略：未知工具/参数失败可以转成安全 ToolResult 供模型修正；context 取消和 Runtime 内部失败终止运行。原始内部错误保留在受控诊断中，模型只接收脱敏摘要。先顺序执行；不要自动重试可能写入外部系统的工具。为每次调用派生超时 context 并释放 cancel，说明超时不等于外部副作用已撤销。

20 分钟 · 接回 Agent Loop

在 loop_test.go 用脚本模型测试：模型第一轮返回 SearchKnowledge 和 GetDocument 调用；执行器得到结果后，Loop 追加 assistant 原始 ToolCalls 与匹配 ID 的 tool messages；第二轮模型生成答案。若 GetDocument 依赖检索得到的 ID，应安排在后续模型轮次，不能假定同批调用存在数据依赖传递。

15 分钟 · 并发策略与中间件设计

在 design.md 对照 Eino ExecuteSequentially、ToolCallMiddlewares：独立只读调用未来可以有限并发；有依赖或有副作用的调用先顺序执行。并发完成顺序不能破坏结果关联。画出审计/权限检查 → 超时 → Invoke → 结果整形的包装链，权限拒绝必须发生在调用之前。今天只实现顺序版本；并发和审批分别留给后续课程。
