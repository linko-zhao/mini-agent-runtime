为什么工具能调用了，还要学执行器？

今天要能回答：模型一次提出多个工具调用时，Agent 怎样先判断这批请求是否可执行，再逐个执行、关联结果，并正确决定继续还是停止？

Day 08 解决了“能力如何描述、注册和接入”：模型给出名称与参数，Runtime 找到工具，工具通过 Store 访问后端。接下来用户要求“比较两份已知文档”，模型可能一次返回两个 get_document 调用。这时仅有统一 Invoke 接口还不够：哪个结果对应哪次请求？后一项名称错误时，前一项是否已经执行？某项失败后，还要不要继续？

最直接的办法是边遍历边执行，但这样会把协议检查、业务调用、超时和消息拼装交织在 Loop 中。今天把一批调用到一组结果作为执行边界：Loop 决定何时调用模型、何时结束；执行器组织工具调用；工具只处理自己的业务能力。执行器可以先是同包私有方法，不必立即设计成大型框架。

学习顺序：先手算下面的双调用过程，再用反例理解批次检查和错误策略，最后阅读 Eino 并沿累计示例提取执行边界。今天不改变既有公开接口和错误语义。

概念前置：ToolCall 的 ID/Name/Arguments、assistant/tool 消息、context。前序编码未完成时，可使用 examples 参考基线继续理解，不新建每日 Module。

先把一次批次调用走通

场景：用户已经提供 doc-a 与 doc-b 两个 ID，请 Agent 比较正文。它们是独立读取，可以在同一批提出。下列是教学消息示意，示例基线尚未提供这个双文档 Demo；Day 08 的 knowledge 入口仍是三轮“检索 → 读取 → 回答”。

Loop → Model.Generate(历史)
     ← assistant.ToolCalls = [
          {ID:"read-a", Name:"get_document", Arguments:{"id":"doc-a"}},
          {ID:"read-b", Name:"get_document", Arguments:{"id":"doc-b"}}
        ]
Loop 保存原始 assistant 消息
     → 执行器：检查整批 ID / 已注册名称
        → 顺序 Execute(read-a) → Invoke → Store.Get(doc-a)
        → 顺序 Execute(read-b) → Invoke → Store.Get(doc-b)
     ← [tool{ToolCallID:"read-a", Content:正文A},
        tool{ToolCallID:"read-b", Content:正文B}]
Loop 追加 tool 消息 → Model.Generate(完整历史) → 比较结果，无调用则结束

三个角色：Model 产生调用意图；执行器把同批请求变成带原始 ID 的结果；Loop 把结果放进历史并启动下一轮推理。工具名称相同也没关系，read-a 与 read-b 区分两次调用。

有依赖时怎么办？若文档 ID 需要先检索才能获得，应像 Day 08 那样先执行检索，将 ID 交给下一轮模型，再请求读取。在同一批里按顺序执行，并不会自动把第一项输出填进第二项参数。

先预测：把第二项工具名改成未注册名称。本课程采用“整批名称/ID 校验失败则终止”的策略，所以第一项也不执行。若先执行第一项再检查第二项，已经产生的外部操作无法靠返回错误撤销。

执行器的设计说明：每道边界解决什么问题

选择为什么这样做与代价本日边界
先检查整批，再开始执行避免可提前发现的协议问题导致部分调用已发生。代价是某一项协议错误会阻止本批其他合法项。检查 ID 非空且批内唯一、名称已注册。工具内部校验业务参数，因此不保证所有参数错误都在批次执行前发现。
先顺序执行容易跟踪调用与取消，减少并发策略干扰。代价是独立读取的总耗时更长。并发是后续调度策略；顺序执行不等于事务，也不解决参数依赖。
复用 model.Message 作为结果Loop 已经消费 tool 消息，继续使用 Role/Content/ToolCallID，避免另建一套 Result 再转换。工具返回内容；执行器填 Role=tool 与原始调用 ID；Loop 管理历史。
按现有契约分类失败参数/业务失败可反馈模型；取消必须阻止后续调用；内部原始错误不能直接暴露。统一行为后才容易演进策略。沿用下表，不照搬 Eino 默认行为，也不在本页静默更改错误契约。
从 Loop 中提取私有方法获得清晰边界，同时复用已持有的注册快照、超时与事件配置。暂时仍依赖 Agent，未来需要独立复用时再提取对象。agent.New / Run、Tool.Execute、Meta/Invoke 和消息类型保持不变。

失败后到底发生什么？

情况本课程的处理模型是否继续收到结果
缺失/批内重复 ID、未注册名称整批预检查阶段终止 Run，工具执行次数为 0本轮不继续调用模型
工具返回受控 tool.Error（参数/业务错误）转成受控文本，保留本次 ToolCallID，继续后续工具是；模型可据此修正，是否修正仍取决于模型
工具返回未知内部错误回填固定摘要 execution_failed: tool execution failed是；不传原始错误或凭据
取消或超时通过 errors.Is 识别并终止 Run，不执行后续工具不把取消包装成普通工具结果继续推理

不要混淆：整批预检查只能拦住此处检查的问题；执行到第二项才发现参数错误时，第一项可能已执行。超时和 Run 失败也不表示外部操作已回滚。本节没有事务、补偿或自动重试。

可见性与授权：Day 08 的 WithVisibleTools 过滤描述，不删除执行注册。今天仍按完整注册表检查名称；真正“本轮是否允许执行”的授权检查留给 Day 11，并须在执行前落实，不能拿可见集合代替权限。

任务二 · 25 分钟：迁移顺序执行与错误整形

为什么做：所有工具需要一致的调用 ID、context 和错误处理，避免每种业务工具自行决定 Agent 是否继续。

操作与观察：15 分钟把 agent.go 中的顺序调用、子超时 context、cancel 释放与工具开始/完成事件迁入方法；5 分钟按上表处理错误；5 分钟核对取消后不会执行下一项。保持 Event 的 Step、ToolName、ToolCallID 和终态发布职责不变，避免 Loop 与方法重复发工具事件。

完成证据：成功时按输入顺序返回消息；受控错误与未知内部错误分别回填；errors.Is 可识别取消/超时；cancel 在每次调用后释放，超时仍是合作式取消，不声称能强杀工具。

任务三 · 20 分钟：把结果接回 Loop，并观察下一轮输入

为什么做：执行成功只有回到模型可见历史，才能帮助 Agent 继续解决用户问题。

操作与观察：10 分钟修改 Run：保留原始 assistant 入历史，调用 executeBatch，成功后追加其返回消息；遇到 error 直接按既有失败路径终止。10 分钟在 agent_test.go 用记录输入的脚本模型构造双 get_document 调用，断言第二轮收到原始 assistant 加 read-a/read-b 两条 tool 消息，最后返回文本。

迁移顺序：先复制原执行块到新方法并整理局部返回值；再将 Run 原块替换为单次方法调用，删去重复逻辑；最后核对事件与错误行为。agent.New / Run 的签名、各入口调用方和旧工具适配均无需修改。

完成证据：模型第二次输入包含完整调用与结果，两个相同名称工具的结果仍按 ID 区分。若第二项取消，Loop 终止；第一项已经发生的外部操作不会撤销。

任务四 · 15 分钟：说明未来策略应接在哪里

为什么做：理解搭建思路意味着能面对新增需求定位改动，而不把策略散落进所有业务工具。

操作与观察：10 分钟在 design.md 画出“未来执行授权 → 超时包装 → Execute/Invoke → 结果整形”的位置，对照 Eino 中间件；5 分钟说明独立读取可有限并发、依赖读取需后续模型轮次，以及写入调用不能随意重试。今天只保留既有顺序、无自动重试行为。

8 分钟复盘：先合上代码作答，再展开参考思路。

为什么不能边检查边执行？整批检查是否等于事务？

后项缺失工具或重复 ID 可提前发现，先执行会造成可避免的部分操作。但检查无法保证后端不失败，业务参数也可能到 Invoke 才发现错误，因此不是事务，也不提供回滚。

同批顺序调用能自动实现“先搜索再用搜索结果读全文”吗？

不能。两条调用的参数在模型返回时已确定；若 ID 来自搜索结果，应把搜索结果传给下一轮模型后再产生读取请求，或显式设计组合能力。

明天加超时、重试或授权，应该改哪里？

围绕统一执行入口设计策略，不让每个业务工具重复承担调度。超时不代表撤销；写操作重试要先考虑幂等；授权检查必须发生在执行前。Loop 继续负责模型与消息迭代。
