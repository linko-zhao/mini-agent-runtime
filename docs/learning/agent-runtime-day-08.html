Go 编码任务（按时间盒推进）

任务 A · 15 分钟：核对协议数据结构

internal/model/model.gointernal/model/openai/convert.gointernal/tool/tool.go

跟踪 ToolDefinition → OpenAI request → response ToolCall → Agent 分派 → tool role 消息。核对 ToolCall ID 和工具名如何保存，查看当前测试使用的消息角色与函数参数编码。列出不变量：响应必须引用请求 ToolCall ID；每个调用最多执行一次；工具名称必须命中本地注册表。

任务 B · 25 分钟：设计清晰的工具错误边界

在 internal/tool/tool.go 附近为工具协议错误确定稳定约定（可使用 sentinel 或包装错误类型，不必暴露底层敏感数据）。至少区分：JSON 参数无法解码、参数字段缺失/超范围、工具未注册、工具内部执行失败、Context 取消。Agent 是否把可恢复工具错误回填给模型，要结合现有 API 行为测试；取消则应作为 Run 终止边界处理，不能静默当作普通字符串结果。

任务 C · 25 分钟：增强一个真实 Tool 的参数校验

先检查 internal/tool/calculator.go 的参数结构与实现，再为其补充严格解析：拒绝非法 JSON、缺失必需字段、额外字段（若当前协议允许则明确记录）、零值歧义以及不支持的运算符。使用 json.Decoder.DisallowUnknownFields 或有明确理由的替代方案；校验失败时返回可测试错误。不要把模型提供的工具参数视为可信输入，也不要增加第三方 Schema 校验库。

任务 D · 15 分钟：对齐工具定义与实现

在 calculator 的 Definition 中保证名称、参数名、required 和运行时校验完全一致。检查模型适配器发出的 JSON 是否保留定义；不要自行改动 OpenAI 对话协议格式。必要时只添加少量说明到 docs/design.md，避免把本地授权、安全策略交给模型判断。

核心协议往返：Agent 收集 DescribedTool.Definition → Model 请求带工具列表 → 模型返回带 ID 的 ToolCall → 应用根据 Name 查表并校验 Arguments → Tool.Execute → 生成 Role=tool、ToolCallID 匹配的结果消息 → 下一轮模型请求。工具定义让模型知道“如何请求”，不会替代应用的输入验证或权限检查。
