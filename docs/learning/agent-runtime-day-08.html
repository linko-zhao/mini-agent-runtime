Day 08 / 56 · Agent 工具抽象与 Eino 接口设计

把 Tool 视为 Agent 访问外部能力的契约：元信息供模型选择，执行接口供 Runtime 调度，业务实现负责实际访问。

阅读 20 分钟编码 80 分钟测试复盘 20 分钟

先理解今天要解决什么问题

今天要能独立回答：一个已经会与模型对话的 Agent，怎样接入新的外部能力，而不用每加一个工具就改一次 Agent Loop？

第一周建立了“调用模型 → 判断是否有 ToolCall → 执行工具 → 把结果交回模型”的循环。现在用户要求“查找并阅读 Runtime 工具契约”：模型只有已有知识，无法直接读取你的资料库；你需要把检索和读取变成它可选择、Runtime 可执行的能力。

最直接的实现是在 Loop 里写 switch call.Name，逐个调用搜索、数据库、HTTP。少量工具时可行，但工具增加后，Loop 会混入参数解析、后端连接和业务逻辑。今天通过工具契约把这些变化放到各自的层：模型提出调用意图，Runtime 组织执行，工具适配业务能力，Store 访问后端。

学习顺序：先看下面的一次完整往返，再带着问题读 Eino，最后沿参考示例完成四项增量练习。页面能独立解释设计；代码用于验证理解。若已有累计示例，先遮住实现写出自己的接口草图，再比较差异，无需重新建工程。

概念前置：Model.Generate、消息历史、assistant/tool 角色、context。它们分别表示“请求一次模型”“保留往返上下文”“区分调用与结果”“传递取消和超时”。课程按路线推进，前序编码未完成时可使用 examples 参考基线继续理解。

把 Agent 的一次工具往返走通

用户输入：“查找并阅读 Runtime 工具契约”。先区分两个阶段：启动时装配能力；运行时由消息推动循环。

装配：Store → SearchKnowledge / GetDocument → Registry.Register
      → Registry.Tools() → Agent.New → ToolDefinition → Model.ToolBinder

运行：用户问题 → Model.Generate(消息历史)
      → assistant ToolCall → Loop 查注册表 → Tool.Execute
      → 适配层 Invoke → Store → 工具结果
      → tool 消息（ToolCallID 对齐）→ Model.Generate → 调用下一工具或回答

Registry.Specs(可见名称) 可以单独查看描述快照；当前 Agent 构造路径通过 Registry.Tools() 适配为旧接口，再由 Definition() 取描述并按 WithVisibleTools 过滤。两者说明同一条边界：给模型的是描述，本地保留的是执行对象。

  1. 装配：注册 search_knowledge 和 get_document。描述告诉模型“什么时候用、参数是什么”；此时不搜索、不读取资料。
  2. 第一轮：模型返回 {ID: "search-1", Name: "search_knowledge", Arguments: {"query":"Runtime"}}。这是一份调用请求，尚未访问后端。
  3. 执行与回填：Runtime 查本地工具，传入参数和本次 context；Store 返回 doc-1 及摘要。Loop 保留 assistant 原始调用，并追加 Role=tool, ToolCallID="search-1" 的结果消息。
  4. 第二轮：模型获得检索结果后，才能请求 get_document({"id":"doc-1"})，调用 ID 为 read-1。该结果用 ToolCallID="read-1" 回填。
  5. 第三轮：模型读到正文后返回最终文本；无 ToolCall 时 Loop 结束。检索和读取有数据依赖，不能假定同一批调用自动传递 ID。

理解检查：工具名称用来找到能力，调用 ID 用来找到“这一次调用”的结果。同一个工具可以被调用多次，所以只用名称关联结果会产生歧义。

示例的观察范围：examples/cmd/knowledge/main.go 使用脚本 Mock 预设上述三轮响应，验证 Runtime 能接好线路；它不证明真实模型会选择正确工具。接真实模型还需要支持 ToolBinder 的适配器，以及清晰的描述与参数协议。

为什么要拆成这些层

设计解决的问题与取舍如何验证理解
Spec / Meta：描述能力模型需要名称、用途和输入格式。将描述与执行分开，枚举能力时就不会访问业务后端，也不需要把 Go 函数或凭据发给模型。代价是必须维持描述与实际参数校验一致。调用 Meta / Specs 后，Store 调用次数仍为 0。InputSchema 是输入约定，不能替代 Invoke 的实际校验。
Invokable.Invoke：执行能力Runtime 只依赖统一入口，可调度检索、HTTP 等不同工具。工具自己解析业务参数；Runtime 保留调用 ID、消息和控制流职责。把 Store 换成另一个实现，Loop 和 ToolCall 结构不变。
Registry：名称到实现把名称解析从 Loop 的业务分支移到注册表。重名若被覆盖，同一调用可能执行错误实现，因此入口拒绝重复；schema 仅做基本结构检查。重复名注册失败；Specs 顺序稳定，修改返回值不会改写内部描述。
Store：业务后端端口Search/Get 定义工具需要的后端能力。Fake 与真实后端可替换，网络和凭据配置留在适配层；代价是多一层接口，但离线测试更容易。FakeStore 能完成检索与读取；换后端只需适配 Store，不改 Agent 协议。
Adapt：兼容已有 LoopDay 01 的 Execute 和 Day 03 的 Definition 已被使用。把 Meta/Invoke 转成旧接口，可增量演进，无需同时重写调用方。追踪 Execute → Invoke，执行 context 原样传递；构造时的 context 不替代运行时 context。

今天的边界：只建立同步工具接入。流式输出、批次执行器、执行授权、重试和 MCP 分别在后续增量加入。模型可见过滤用于提供选择范围，当前执行表仍保留隐藏工具；真正的权限检查必须在执行前另行实现。

任务一 · 20 分钟：先设计工具契约

为什么做：让模型选择能力和 Runtime 执行能力共用工具身份，同时保持不同职责。先写下“模型应看到哪些字段”，再看 examples/internal/tool/contract.go：

// 接口摘录，非独立可运行文件；完整定义见 contract.go。
type Spec struct {
    Name, Description string
    InputSchema json.RawMessage
}
type Described interface { Meta(context.Context) (Spec, error) }
type Invokable interface {
    Described
    Invoke(context.Context, json.RawMessage) (string, error)
}
// Call 沿用 model.ToolCall；Adapt 将 Meta/Invoke 接为 Definition/Execute。

操作与观察：用 5 分钟画接口、10 分钟实现或对照 Meta/Invoke 与 Adapt、5 分钟追踪新工具如何接进旧 Loop。复用 ToolCall，不再定义第二套 ID/Name/Arguments。

完成证据：能够说明 Spec 中为什么没有执行函数和凭据，以及调用 ID 为什么属于调用消息而非业务输入 schema；在适配器中找到本次 Execute context 进入 Invoke 的位置。

任务二 · 20 分钟：把能力接到注册表

为什么做：模型返回的是名称；本地必须有确定的名称到对象映射，同时注册集合与模型可见集合可能不同。

操作与观察：用 10 分钟实现或对照 examples/internal/tool/registry.go 的 Register / Specs / Tools，5 分钟查看 examples/internal/agent/options.go 的 WithVisibleTools，5 分钟手算“注册 A、B，只展示 A”时两份集合的内容。Specs(nil) 枚举全部，非 nil 空集合枚举零个。

完成证据：能解释重名为何拒绝、枚举为何不执行工具、描述为何返回副本；隐藏 B 后仍能在完整注册表找到 B，因此可见过滤不能承担授权。

任务三 · 25 分钟：接入检索与读取，并走通三轮对话

为什么做：检索返回文档 ID，读取消费该 ID，可直观看到“工具结果改变下一轮模型输入”。拆成两个工具是今天的教学选择，便于观察依赖；若业务总是同时需要全文，也可设计组合工具，但需重新权衡成本与灵活性。

操作与观察：用 10 分钟实现或对照 examples/internal/tool/knowledge/tools.go 的 Store / SearchKnowledge / GetDocument，10 分钟沿 examples/cmd/knowledge/main.go 追踪注册和三轮 Mock，5 分钟写出每次调用与结果的 ID。FakeStore 用于离线验证，实际后端接入只需实现 Store。

完成证据：画出 search-1 → doc-1 → read-1 的关系；指出工具返回的字符串如何成为 tool 消息，最终回答为什么还需要再调用一次模型。凭据不进入 Spec；取消 context 沿 Runtime → 工具 → Store 传递。

8 分钟复盘：先自己回答，再展开参考思路。

为什么模型返回 ToolCall 后，还需要 Runtime？

ToolCall 只表达名称、参数与 ID；Runtime 找到本地实现、执行并关联结果，把 assistant/tool 消息保留到下一轮历史。后端调用不会因为模型生成了名称而自动发生。

换检索后端和增加一种工具，分别改哪里？

换后端实现 Store；新能力实现 Meta/Invoke 并注册，必要时调整模型可见配置。两者都不应要求在 Loop 中新增业务 switch。

隐藏工具为什么不能保证它不会被执行？

当前过滤只改变发给模型的描述，完整执行表没有删除该能力。脚本模型或异常请求仍可能返回其名称；执行授权需在调用前检查，留到 Day 11。
