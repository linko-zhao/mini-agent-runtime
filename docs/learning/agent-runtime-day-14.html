为什么今天先整合，而不继续加接口？

能从用户需求出发画出完整Agent数据流，用消息、调用次数和事件共同判断行为，并解释需求或故障变化时应改哪一层。

Day08–13已经建立工具描述/执行分离、注册与批次调用、策略包装、执行授权、MCP会话和适配器。如果只分别测试每个类，很容易忽略连接处：授权拒绝之前是否已经发出远端请求？工具失败是否必然使Run失败？模型下一轮拿到的是正文、错误还是错配的调用ID？

场景：用户已给出local-1与remote-1两个文档ID，要求比较正文。因此模型可以在同一批提出两次独立读取。若ID必须先检索得到，应安排后续模型轮次；顺序执行不会自动把前一个结果注入后一个参数。

今天不新增Runtime公共接口。代码增量是可运行集成夹具、断言和设计记录，业务仍复用GetDocument/FakeStore。课程按设计进度推进，不以根internal/cmd学习者代码的完成状态作为发布条件。

运行：

控制权：Host装配可信上下文、注册与MCP会话；Loop管理消息和模型轮次；授权决定能否执行；Policy限制调用；适配器转换协议/结果；Server负责业务与后端资源权限。

测试分别解析本地Document JSON与远端ResultEnvelope，保持Day13的输出契约。MCP整数请求ID独立于模型ToolCallID；Principal不会被塞进工具arguments。

脚本模型最后返回的字符串是测试夹具输出，不证明真实模型正确完成文档比较。每个场景还要检查实际调用、第二轮历史、错误投影与唯一Run终态。

先预测：一次故障会影响哪一层？

在看参考计数前，为每种场景写出本地Invoke、tools/call尝试、远端Invoke和模型调用次数，再写出Run终态。

  1. 两份读取都成功。
  2. 远端能力没有宿主授权规则，但两个描述都对模型可见。
  3. 两个模型调用使用了同一个ToolCall ID。
  4. 远端结果超过投影后的字节预算。
  5. 远端工具报告isError=true。
  6. Server已完成读取，但返回损坏的RPC响应ID。
  7. 传输等待到工具调用超时。
展开参考计数与解释
场景本地Invoketools/call尝试远端Invoke模型调用Run终态
正常混合读取1112Finished
远端未批准0001Failed
重复模型ID0001Failed
结果预算1112Finished，tool受控错误
远端业务失败1112Finished，tool受控错误
执行后响应损坏1112Finished，Client failed
远端超时1101Failed，DeadlineExceeded

tools/call统计传输调用尝试；远端Invoke统计业务方法进入次数，不等于成功提交。超时夹具故意在转发前等待context，所以远端Invoke为0；真实网络超时不能据此推断远端未执行。损坏响应夹具则先执行Server再返回坏ID，展示错误不会撤销已经发生的调用。

如何理解“Run结束了，但工具有错误”？

按已有契约，结果预算、MCP业务失败和适配后的协议错误可作为受控tool消息回填，脚本模型随后返回文本，因此RunFinished。这个事件只表示Run以文本返回，业务目标是否完成还需检查结果和需求验收。取消、授权拒绝、模型调用ID错误则终止Run。

MCP响应损坏会令Client失效；适配器回填安全摘要后，Run仍可能结束。客户端会话状态与Run状态不同，失败会话的后续探针不应产生协议发送。不能把所有层压成一个“成功/失败”标志。

如何理解“授权允许，却没调用工具”？

授权循环先检查完整批次。第一项读取获得允许，第二项远端能力因未配置规则被拒绝，于是整个批次零执行。允许决策是判断记录，不是执行承诺。初始化和目录发现此前可能已有协议流量，零执行断言专指业务tools/call。

8分钟理解验收：合上代码回答，再看提示：

为什么描述可见、调用允许、执行完成必须分开？

描述供模型选择；授权基于可信主体和能力规则；执行结果由实际调用返回。允许决策不能证明执行发生，Run返回文本也不能证明用户目标已完成。

当前测试为什么不能证明真实模型会正确比较文档？

脚本模型只提供确定的调用和结束文本。测试核对协议和历史输入，不评估真实模型选择、推理或答案质量；后续评估需要真实模型/数据与独立质量标准。

如果进程在Server执行后、响应入历史前崩溃，保存messages就够了吗？

需要区分已确认与不确定调用、恢复位置和外部副作用；仅重跑Loop可能重复操作。连接对象、context和本地变量也不能直接当作持久恢复协议。
