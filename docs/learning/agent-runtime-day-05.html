任务 B · 15 分钟：定义 Event 与 EventSink

internal/agent/event.go（新增）事件只携带可安全观察的元数据：类型、步数、时间、工具名称、ToolCall ID、耗时和分类状态。不要直接放入完整 Prompt、工具参数、工具返回值或 API Key。

// internal/agent/event.go —— 仅给出建议结构，具体常量自行定义
type EventType string // RunStarted、StepStarted、ModelCompleted、
// ToolStarted、ToolCompleted、RunFinished、RunFailed

type Event struct {
    Type       EventType     // 事件类型
    Step       int           // 当前模型调用轮数，从 1 开始
    At         time.Time     // 事件产生时刻
    ToolName   string        // 工具名称，非工具事件可为空
    ToolCallID string        // 与消息历史中的 ToolCall.ID 对齐
    Duration   time.Duration // 模型或工具执行耗时
    Status     string        // ok、error、cancelled 等非敏感状态
}

type EventSink interface {
    Emit(ctx context.Context, e Event) // 同步发布，先不引入异步队列
}

建议在 internal/agent/options.go 提供 WithEventSink(sink EventSink)，通过 New(..., opts ...Option) 保持原有构造调用兼容。也可以增加 NewWithOptions，但不要破坏 Day 01～04 的测试。

任务 C · 25 分钟：在 Agent Loop 中注入事件

internal/agent/agent.gointernal/agent/event_test.go

从 Run 开始发出 RunStarted；每轮调用模型前发 StepStarted，成功返回后发 ModelCompleted；每个工具执行前后分别发 ToolStarted 和 ToolCompleted；最终只发一个 RunFinished 或 RunFailed。建议使用命名返回值与 defer 集中处理终态事件，避免每个错误分支重复发布。

// 建议辅助方法：sink 为 nil 时不产生事件
func (a *Agent) emit(ctx context.Context, e Event) {
    if a.sink == nil {
        return
    }
    a.sink.Emit(ctx, e)
}

// 在工具执行前：先检查 ctx.Err()，再发布 ToolStarted。
// 工具错误若按现有策略回填给模型，发布 ToolCompleted(error)，
// 不要错误地同时发布 RunFailed；只有 Run 真正返回错误才是 RunFailed。

本日事件语义：回调在当前 Run goroutine 内同步执行，保证同一次 Run 的事件顺序；Sink 不能阻塞过久。共享 Sink 可能被多个 Run 并发调用，收集器需要互斥保护。教学阶段假设 Sink 是可信代码；Sink panic、背压、异步队列、丢弃策略和 SSE 留到后续迭代。
