为什么Run只返回文本和error还不够？

能区分Run控制状态、调用观测状态和外部业务结果，解释状态转换约束，并在保留旧接口的基础上取得一份独立的最终快照。

Day14已经看到：工具结果超预算时，模型仍可收到受控失败并返回文本；批次第二项超时时，第一项可能已经执行。若只看Run的两个返回值，宿主难以说明哪些调用已返回、哪些未开始、哪些结果尚未进入模型历史。

今天新增RunWithState，原Run继续委托同一执行路径。每次执行有私有record，集中持有Step、Messages和Calls。它描述Runtime观察到什么，不是新的业务成功判定器。

本日只提供正常/错误返回时的最终内存快照，没有运行中查询、写盘、恢复或重放入口。进程在返回前退出，内存记录仍会丢失；Checkpoint、版本化存储和恢复位置随后按课程推进。

先走通完整过程：状态在原闭环中更新

Host → RunWithState(ctx,input)
 → 创建本次RunID与私有record：created → running
 → Generate(record.Messages) → 保存assistant
 → 记录整批Calls为planned → ID/名称检查 → 授权
 → 执行器：
     planned → running → returned / errored
                         └ 取消后无已接受结果：unconfirmed
     未开始就终止：blocked
 → 完整批次结果进入Messages → 下一轮Generate
 → 正常文本：Run completed；控制错误：failed/cancelled
 → Clone最终RunSnapshot → 返回Output、Snapshot、Go error

原Run(ctx,input) → 同一路径 → 只返回Output与Go error

Model/Message/ToolCall、Meta/Invoke、Registry、Policy、Authorizer和MCP适配保持不变。RunID标识这次观测；模型调用ID继续原样保存，不用RunID替换它，也不拿RunID当业务幂等键。

Step表示Loop当前进入的轮次，不是成功请求次数。例如预取消可能进入第1轮就停止，实际Model调用仍为0；调用次数要结合事件或测试探针判断。

先把状态语义说清楚

Run：控制流程有没有结束？

created → running → completed
                  → failed
                  → cancelled
终态不允许重新进入running，也不允许重复完成。
状态本课含义
completedRun以文本正常返回；工具受控错误可以同时存在，业务目标仍需另行验收
failed模型/协议/授权/步数等控制错误停止Run，保留Go错误链
cancelledcontext取消或超时；FailureClass区分cancelled与deadline_exceeded

CanTransition显式限制迁移。成功结束时若还有未完成调用，守卫会产生ErrInvalidTransition并失败结束，不把内部状态缺口标为成功。

Call：Runtime对一次调用观察到了什么？

状态含义与边界
planned模型提出，已记录，尚未通过全部检查和开始执行
runningRuntime已进入工具执行路径
returned接受了无error的工具返回；不单独证明外部事务状态
errored接受了错误返回，并保存受控tool消息；不表示操作从未发生
unconfirmed调用已开始，但取消/超时后没有已接受结果；不能自动重放
blocked本次Run没有开始执行它，例如整批预检查失败或前项取消后的后续项

这些状态不能直接推出远端写入提交或回滚。unconfirmed特别标出取消后的结果不确定；其他错误也可能伴随已发生的外部效果。Caller的业务契约、幂等和恢复确认仍独立存在。

成功创建并启动Run后，执行错误也会带回终态快照。随机ID构造失败时尚未启动Run，返回错误和零值Result，不能把空RunID当成已有运行记录。

最重要的边界：结果已返回，不一定已进入模型历史

假设同批是[first, wait, third]：first返回，wait超时，third未开始。原批次语义是出现取消就停止，不把部分结果回填给下一轮；今天保留这一行为，而不是为了状态记录改掉执行策略。

位置Call状态Calls.ResultSnapshot.Messages
firstreturned保存已接受的tool消息保留user+assistant调用请求；本批部分tool消息未进入Loop历史，没有下一轮模型
waitunconfirmed无迟到结果
thirdblocked无结果

因此，不能根据历史里没有某条tool消息推断该工具从未执行。Snapshot.Calls保留这类观测，但当前还没有重放或恢复决策。Call记录用Step+Index定位，Index在批内从0开始；即使模型给出重复ID，也保留各位置，不用ID做会覆盖记录的map键。

为什么返回副本，为什么不把状态放进Agent字段？

Agent可被并发Run复用，若把Messages或当前状态写在共享Agent上，会串请求。今天每次Run单独创建record，模型/工具仍需遵守前序的并发契约。测试中的并发模型是无状态函数，不是共享带游标的Mock。

Snapshot.Clone复制消息切片、嵌套ToolCalls参数和Calls.Result指针。调用方能修改自己的副本，原响应或另一个Run不会被牵连。字符串沿Go不可变值语义共享；记录与复制有分配成本，不是零成本或并发事务机制。

快照含输入、参数和正文，是宿主的运行数据，不是公开审计事件。FailureClass只存受控类别，不复制原始Go错误文本；真正错误仍在第二返回值保留errors.Is/As语义。将来存储快照时需要另外定义数据访问、序列化与保留策略。
